# Play mode: the original in-game city UI (research, 2026-10-27)

Data: `data/play/ui.json` (generated by `re/venv/bin/python tools/play_ui.py` from Zeus.exe + atlases).
Check: `python3 tools/play_ui_composite.py OUT_DIR [WxH ...]` composes the UI from ui.json + sprites only.
Scope: the city screen (top bar, control panel, build menus, info windows, frames, minimap, overlays).
Not covered: main menu, world map, advisor screens, fonts/text rendering (other task), page-specific
widgets inside the info box (wage arrows, trade lists, military lists).

Sprite refs follow docs/play-mode.md: `{file, index}` = atlas index (index counts the 200 system images).
Packed group ids in the exe are `collection*512 + rank`; rank = atlas group id (checked: Zeus_Fonts,
Zeus_Interface, Zeus_General have no empty groups before the last one). Collections: 0 Zeus_Fonts,
1 Zeus_Interface, 2 Zeus_Unloaded, 3 Poseidon_Unloaded, 4 Zeus_General, 5 Zeus_Terrain, 51 SprMain,
52 Poseidon_Loaded, 53 PoseidonImps (bank list at decomp line ~278653, loader `0x005AC3A0`).

## Evidence levels
- **exe**: read in the decompile/disassembly or in a data table of Zeus.exe (address given).
- **seen**: measured on a real screenshot of the original (the oracle, below), by exact sprite matching.
- **arm64**: refs/zeus-poseidon-arm64 docs (`docs/engine/interface.md`, `src/win32/widescreen.cpp`); many of
  those are themselves verified natively there.
- **eZeus**: not used for numbers (only to cross-check names).

## Ground truth: oracle screenshots
The oracle (docs/re/oracle.md) runs the real exe and the `shot FILE.bmp` script action captures a frame.
Base script: the "See a working city" tutorial, then Options > Display options > 1024x768:
`5:key 27; 12:click 220,101; 17:char 78; 20:click 556,320; 27:click 644,523; 33:click 588,476; 45:rclick 300,300; 50:click 90,10; 52:click 120,41; 55:click 320,253`
Rules learned: start each run with an empty `--write-dir` (the game saves the display mode and player);
the `click` action is unreliable on the panel, use `move X,Y; +0.5 down X,Y; +0.5 up X,Y`; right click
on a panel button opens its help page. Every page, every build submenu, hover/selected states, the
radar tab, a building and a walker info window, the Options dropdown, messages and goals windows were
captured at 1024x768 (and the city at 800x600). All panel buttons, frames, the submenu bars, the
top-bar icons and the info-window corners/buttons were located by exact pixel matching of the
extracted sprites (tolerance 24/255): positions in ui.json marked "seen" are those. The composite of
ui.json matches the oracle shot pixel for pixel on every non-text sprite (panel button column 100 %,
lower row 100 %, god art 100 %, submenu bars 100 % outside the text; differences = text and live data).
Web screenshots were not needed (the oracle is exact); none were downloaded.

## 6. Minimap (`0x00454980`)
128x110 px at (panelX+50, 165) (radar tab) or (panelX+50, 318) (overview page). One tile = 2 px wide,
1 px tall (diamond rows offset by 1 px). Grid (`0x00449FF0`, rotation 0): 0xE7 cells x 0x1C9 rows; tile (x, y)
-> cell (0xE6 + x - y)/2, row 1 + x + y, i.e. 1 px per iso row (not per 2), odd rows drawn 1 px left; cells
outside the play area are a filler drawn with `SPR_R_SPACE` image 0. The play-area bounding box (cells
0x007D3B84..7C, rows 0x007D3B80..78) limits scrolling: the window is centred on the main view and clamped to
it, or centred on the grid when the box is smaller (`0x004547C0`, rows even). View rectangle at
(left + (view col - first col)*2, view row - first row), view cols*2 x view rows (`0x00509870`).
Ours also draws it over the god art at the panel bottom (12,605) 166x155, on by default (`UIX.godMap`;
user request, not the exe: the exe starts on the overview tab, 0x00510ED0 sets 0x00FA0000 = 0).
Each tile copies the first 2 pixels of a `SPR_R_*` image: terrain
by flags (grass, scrub, river, deep water, woods, rock kinds, marble quarry, dunes, meadow, cliffs, road,
lava/fertility), buildings by per-type group (`g_building_type_info[type][7]`: R_COMMON_HOUSE,
R_ELITE_HOUSE, R_HUSBANDRY, R_INDUSTRY, R_DISTRIBUTION, R_SAFETY, R_ADMIN, R_CULTURE, R_MYTHOLOGY,
R_MILITARY, R_AESTHETIC) drawn at the building's draw tile by size, figures as dots and god/monster/hero
icons. The red (0xF800) rectangle shows the main view. Decision order and groups: ui.json `minimap`. **exe**
(order read; some flag names from docs/logic/map-terrain.md; the dot colours by climate partly hypothesis).

## 9. Held buttons (exe read 10-28, bugs.md 165; ui.js uiRepeat)
mouse_poll 0x0050B470 keeps the left button's state: held 0x00F2A704, press edge 0x00F2A707, release edge
0x00F2A708 (right button: 0x00F2A6F8 / 0x00F2A6FB / 0x00F2A6FC). Widget lists come in three kinds:
- **widget_hit_test / widget_click_dispatch** lists (most buttons, the military panels included): fire on release, no repeat.
- **FUN_004319C0** lists: fire on release; a record of type 6 also fires on every call while held over it
  (no pacing; which widgets use type 6 is not mapped).
- **FUN_00431C80** lists, the arrow buttons: fire on the press with counter 0 (+0x12, passed to the handler in
  0x00F135F0); then while the button stays down over the same button (0x007818A0), on each UI tick the counter
  goes up and the handler fires if table 0x005F0028[counter] is 1 (counters 8, 14, 19, 23, 26, 29, 32, 34, 36,
  39..46), and on every tick from 48 on (kept at 47). The UI tick is screen_input 0x00514C10's flag 0x00F9F9A0:
  true on a frame when more than 29 ms passed since the last tick (timeGetTime). Off the button nothing counts.
  So a hold fires at once, after ~8 ticks (~0.25 s), then faster, and from ~1.5 s on every tick (~30 times a
  second; the exact rate is the exe's frame pacing, not measured).
  Lists of this kind: storage limits 0x01607560, trade limits 0x016073A0 / 0x01607480, the next/previous trade
  building pair 0x0065B800 (not in play mode), tax and wage 0x0063DF10 / 0x0063DF48 (panel_click 0x00517650),
  labor priorities 0x006434D0 (FUN_00590B70), and some dialogs not in play mode (screen_input 0x005EFB50,
  0x005EFAE0, 0x005EFC68, 0x00647238; 0x0065C2F0, 0x005EFA50, 0x005ED1A8).
- Ours: a hit pushed with a 7th element `true` repeats (uiRepeat after each UI frame, same table and tick rule);
  marked: storage limits (and our "All goods" row), trade limits, tax/wage arrows, labor priorities. Measured in
  Chrome (60 fps, ticks every 33 ms): a 1 s hold fires 7 times, 2 s 31, 3 s 61 (the table gives 7 / 31 / 61 for
  30 / 60 / 90 ticks). UIX.down is now set (it never was), so the tax/wage and labor arrows show their pressed
  picture while held.

## What the renderer must implement
1. Screen layout from W,H: panelX = W-186; top bar art + extension; panel art + fill below 768.
2. The draw-table widget model: rect, group first, +0/+1/+2/+3 state images, hidden state; hover = mouse in rect.
3. Control-panel state: category tab, page, overlay per page, build-button availability (from the sim),
   undo availability, alert slots.
4. Build submenus: list of available items per menu, C from the widest name, Y0 table, hover style, cost lookup.
5. Frame/highlight tilers (titled, plain, RIMS) and the info-window placement rules.
6. Minimap renderer from the terrain/building grids (server data) with the SPR_R_* first-two-pixel colours.
7. Text (fonts, colours, centring): another agent; positions and font names are in ui.json.
