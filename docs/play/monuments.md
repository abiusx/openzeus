# Play mode: monuments (sanctuaries, Poseidon pyramids, palace)

Data: `data/play/monuments.json`, generated by `tools/play_monuments.py` from
`extracted/model/monument_images.json` (`re/venv/bin/python tools/re_monument_images.py`, an x86 emulation of
the exe's piece classes). Renderer: `viewer/play/monuments.js` (`window.Monuments.draw(out, b, ctx)`).
Sim side: `sim/export.py` adds `pieces` to each monument in `state.json`. Mechanics (stages, materials,
build order): [../logic/monuments.md](../logic/monuments.md). Evidence tags as in [buildings.md](buildings.md):
**exe** = read from Zeus.exe, **emu** = obtained by running the exe's own code in an emulator,
**seen** = checked by compositing PNGs, **guess** = inferred.

## 1. State the renderer gets (sim/export.py)
Each `kind == "monument"` building of `state.json` has `x, y` (min corner of the layout box), `w, h`, `built`
(completion %), `employees` and `pieces`: one `[dx, dy, class, elev, stage, stages]` per layout piece, in layout order
(`data/monuments.json`). `stage` = work stages done = the original's piece stage `b+0x58`; the piece is complete when
`stage >= stages`. Pieces the sim does not build (palace parts 3..6, access pads, extras >= 1000) are `[.., 0, 0]`.
`elev` is the sim's value (0 for sanctuaries: see 3); the renderer takes drawing heights from `monuments.json`.
Sizes: sanctuaries 39 (Dionysus) .. 341 (Zeus) entries, pyramids 10..100, the palace 24.

## 2. How the original draws a piece (exe, emu)
A monument is one building record per piece. Every piece has an image chosen by its class method `vt+0x4C`
(`piece_image(&flags)`), stored in the map image grid by `refresh_piece_image` `0x0053D300` whenever the stage changes:
- `flags & 1`: the image is put on **each tile** of the piece (used for the rough base: image + `grid_random % 6`, and
  for pyramid blocks); `flags & 2` only on the corner tiles (not seen); `flags & 4` makes the tiles walkable (access pad).
- otherwise one n-tile image (`building_footprint_place`), n = piece size (class method `vt+0x00`).
- The city draw loop `0x00458170` draws it as a building top (`0x005ADF00` / sloped `0x0045A690`) at the anchor tile,
  then `composite_draw_extras` `0x0053E5F0`: class methods `+0x48` (`0x005407A0`: working artisans from the `*_conan.txt`
  rows, pyramid lift; not mapped), `+0xF8` and `+0xFC` (animations, section 5).
- Draw point (verified by compositing the priestess and guard animations, which only line up this way): the loop's
  (x, y) is the screen point of the anchor = the **left tile** `(x, y + n - 1)` of the piece, raised by `30 px x height`;
  the top image is placed like every building (`left = tileX(min) - 30(n-1)`, `top = tileY(min) + 30n - h`), the
  animations are placed from the left tile's point.
- Order: by tile row like every object (play: depth = x + y of the bottom tile).

## 3. Heights: sanctuary terraces and pyramid levels (exe)
`grid 0x008E01FA` (sav rank 111) holds a per-tile height, 30 px per step (`y - 30·height`).
- **Sanctuaries and the palace**: at placement `0x0053D300` writes each piece's layout elevation (4th field of
  `Model/Sanctuary_*.txt`, 0..3) into the grid, for the pieces and for the extras (classes >= 1000). Sanctuaries are
  terraced: e.g. Zeus = ground ring 0, platform 1, inner ring 2, temple 3. (`data/monuments.json` stores 0 for
  sanctuaries because the sim does not need it; `monuments.json` `layouts[key].elev` has the real values.)
- **Pyramids** (types 100..114) start flat; each piece of layout elevation e has `E = (e/2)·4` base stages; the level
  rises 2 steps every 4 stages (`pyramid_raise_level` `0x00534750`, all pieces in lockstep in the original). Play: per
  piece `height = e` if `stage >= E`, else `2·floor(stage/4)` (ours: per piece, no lockstep; same picture when the
  level is complete).
- Extras tiles (1000..1006) get terrain flag `0x10000000`; their image is the step rule below (`0x00546380`), or
  the normal terrain when it returns nothing. A step picture replaces the tile's ground in the image grid: FUN_00521520
  writes it into DAT_00D4CFC8 and map_tiles_update_images 0x0051F450 skips 0x10000000 tiles, so the exe draws no
  ground under a step. Play mode (11-02, bugs.md 400): the terrain batch leaves those tiles out (scene.js stepGround,
  play.js buildTerrain; rebuilt when a monument's steps change), the step picture alone is drawn. Checked:
  `tools/step_ground_check.mjs` (readPixels with / without ground under the steps, every monument, views 0/2/4/6,
  zoom 100/200 %, dpr 1.25) and `tools/step_ground_oracle.py` against re/oracle/runs/tut15-steps (scenario
  re/oracle/scenarios/tut15-steps.txt): of the pixels that change, the exe matches the no-ground drawing.
  Ours (11-03, bugs.md 441): a hi-res step picture (Remacri sets) keeps the computed ground under it; the upscale
  erodes the diamond edge that interlocks with the neighbours' at 1x, and with nothing behind it showed a dotted
  black line along the step edges (Aphrodite sanctuary, view 4, 200 %: 344 dark pixels, 9 with the ground). The
  original pictures are drawn exactly as before (0 pixels changed).
- An imported .sav's elevation grid already holds the terraces (0x0053D300 writes layout elevation + the root's base
  +0x6C): savimport resets the piece tiles to the base, since ours raises the pieces when drawing (bugs.md 400).

## 4. Step rule `0x00545940(tile, variant, pyramid)` (exe)
Neighbours N, NE, E, SE, S, SW, W, NW = grid offsets `-228, -227, +1, +229, +228, +227, -1, -229` (`0x005D9888`).
For each: `d = height(neighbour) - height(tile) + 2` (+2 for a neighbour piece whose current level block is full but
not yet raised: not needed with our per-piece heights). `d < 0` or `d > 4` → no image. `d = 3` (one step higher) and
`d = 4` (two) set bit i of a mask and count. Shape = table `0x006411C8[mask]` (in the JSON; -1 = none).
- Only one-step neighbours: shape 4..6 → Poseidon_Loaded `SPR_IMPROVED_TRANSITION_STEPS` + shape − 4, else
  Zeus_Terrain `SPR_TRANSITION_STEPS` + shape (12 images). (Sanctuary terrace stairs.)
- Only two-step neighbours, shape 0..7 (the higher side lies SE, S, SW, W, NW, N, NE, E): Poseidon_Loaded groups
  `G = [STEPS, STEP_VARIANTS, STEPS_BLACK, STEP_VARIANTS_BLACK]`, or the `_BASE` set when the piece is at layout
  elevation 0 and one of its 8 neighbours is not a piece of the monument. Shape 3 (higher to the W: a face looking E): variant 0 → G0+3,
  1..4 → G1+(v−1), 5 → G2+3, 6..8 → G3+(v−6), 9 → G3+3. Shape 5 (higher to the N: a face looking S): 0 → G0+5, 1..4 → G1+(8−v), 5 → G2+5, 6..9 → G3+(13−v).
  Other shapes: G0+shape (v < 5) or G2+shape. So decorations appear only on the two faces turned to the viewer.
- Both kinds at once → none. View rotations 2/6 remap the shape (not needed).
Ours: a completed step piece with no higher neighbour (possible in our sim, where pieces do not rise in lockstep) draws
the flat block top instead of nothing.

## 5. Pyramid base, blocks (exe, emu)
While `stage < E` (not at height) the piece is drawn per tile: stage 0 rough base; else block
`SPR_POSEIDON_PYRAMID_BLOCKS + (stage−1) % 4` (58×45..90: a quarter level more each stage), and when a level is
finished (`stage % 4 == 0`) its flat top (+4, 58×30) at the new height. At `stage == E` (`E > 0`) the flat top; then
the class image. Black marble levels use `_BLOCKS_BLACK` (the sim builds plain marble only).

### 6a. Ambient figures in turned views and orientations (exe + seen, 10-29)
Draw point (x, y) of every figure = the piece's draw point in the current view: its **left-corner tile** on screen
((0, n−1) v0, (0, 0) v2, (n−1, 0) v4, (n−1, n−1) v6 of the n×n piece; city_draw `0x00458170` passes the same point
to the top picture, `composite_draw_extras` `0x0053E5F0` and `animation_draw`), raised by the piece's height. In play
mode: `f = ctx.viewFoot(x, y, n, n)`, `ox = tileX(f.lx, f.ly)` (= the piece picture's left), `oy = tileY(f.lx, f.ly)
− elevPx(f.lx, f.ly) − pixels_per_height·h`. "Turned over" = the figure picture flipped left-right and placed with
`left = P − (w − ax)` for the anchor point P (`0x005AE9F0`; w, ax of the unflipped frame; the SprAmbient frames have
no mirror copies, so the "+0x10 mirror image" branch of both drawers is never taken).

**Priestesses** (`0x0044EE80`, called for every piece of classes 0/1/110/158/159 via vt+0xF8). Class methods:
vt+0xB0 = front (0, 110, 158), vt+0xB4 = back (1, 159), vt+0xB8 = one-piece temple (110), vt+0xCC = grand temple
(158, 159) (`0x00565940` returns 1, `0x00565930` 0). With o = the root's +0x9C (`building_root 0x0049B920`) and

- shown: front piece (0, 158): views {0, 2} if d == 0, else {0, 6}; back piece (1, 159): {4, 6} if d == 0, else
  {2, 4}; 110: every view.
- turned over: views 2/6: d == 0; views 0/4: d == 2.
- position: plain `(x + 58 − ax, y + 26 − ay)`; turned over P = `(x + 2·((W+1)>>1) − 58, y + 26 − ay)`, W = width
  of the piece's current picture (vt+0x4C; all temple pictures are 238 wide → P.x = x + 180, the mirror of x + 58).

## 7. Renderer contract (viewer/play/monuments.js)
`Monuments.draw(out, b, ctx)` pushes `[depth, x, sprite, left, top]`: flat ground tiles at depth `x+y−0.5`, others at
the bottom tile's `x+y`, animations +0.1. `ctx = {sprite, tileX, tileY, elevPx}` plus optional `rand(x, y)` (the
per-tile random used for rough-base variants; Scene.tileRand fits), `data` (default `MAP.monuments`), `now` (ms).
`Monuments.heightPx(b, x, y, ctx)` gives a tile's terrace/level height in px (for walkers on terraces).
To wire: load `data/play/monuments.json` as `MAP.monuments`; add the files in its `files` to `ATLAS_FILES`
(sheets built with `python3 tools/play_atlas.py FILE...`); draw monuments with Monuments.draw instead of
`drawBuilding` (the palace entry of buildings.json would otherwise draw the placeholder frames).

Verified by compositing (node runs monuments.js on exported states, PIL composites; seen): finished and half-built
Zeus sanctuary, Hermes sanctuary, fresh sanctuary (rough base), palace with guard, finished and half-built pyramid 05.

## 7b. Orientation (R key, bugs.md 133)
The exe turns a composite by the placement orientation o (DAT_00DA23C4, stored at b+0x9C by FUN_0053C390):
piece offset (x, y) of size n goes to o1 (y, 1-x-n), o2 (1-x-n, 1-y-n), o3 (1-y-n, x) (composite_offset_rotate,
same in the placement check FUN_0053D9A0). The layout loader FUN_00540110 also precomputes the 4 tile offsets
(+0x18..+0x24) and screen offsets (+0x28..+0x44) of each piece. The piece image depends on b+0x9C
(re_monument_images.py runs vt+0x4C with o = 1..3: temples 0/1/110/158/159, palace front/back, sculptures and
statues change; `orient_phases` in monuments.json). Sim: b.misc["orient"], box w x h swapped for 1/3, pieces
kept box-relative in layout order; play: monuments.js turns them within the box (o1 (dy, W-dx-n), o2 (W-dx-n,
H-dy-n), o3 (H-dy-n, dx)) and picks `orient_phases[o]`.

## 7c. Artisans and construction (10-28)
The sim moves artisans over the monument (route mode 13) to each piece's work tile and exports their look in the
walker record (`sim/export.py` -> `monuments.look`): `["work", t0, end, fx, fy, 0, 0, 0, "build" | "wait"]`, fx/fy
facing the piece. walkers.json `artisan.work.build` = SprMain group 24, frames 0..5 at 2 ticks (`loop`,
`ticks_per_frame`; exe handler 0x004C0060), `artisan.work.wait` = the walk group's frame 3 (exe `first + 0x18 +
dir`); scene.js drawFight plays them. Walkers on a monument are raised by its built height at their tile
(`Monuments.heightPx`, the sanctuary terraces; oracle shots re/oracle/runs/sanctuary-build/shot_460.bmp show
artisans on the raised terrace). Each piece's picture follows its stage (`stage` in `pieces`) as it advances. Carts
are the ox trains of heavy goods, driven to the road entry, where they vanish (exe: hidden, unloaded).
Checked in Chrome (dpr 1.25, baseline copy with a Dionysus sanctuary being built): build frames 1652..1692 step 8
(group 24 + dir 3, 6 frames), wait pose 1572; Athena / Apollo (complete) unchanged.
